# Передача проекта

Короткая выжимка, чтобы продолжить без истории переписки. Общее устройство и запуск — в [README.md](README.md).

Работа с Claude Code: в репо лежит скилл `/tasks-dev` (`.claude/skills/tasks-dev/`) — порядок работы, проверки и правила git; превью — конфиг `tasks` в `.claude/launch.json`.

## Договорённость — сначала прочитать

- **Ничего не пушить.** Работаем локально. Push в `main` сразу деплоит сайт, а прод-база ещё старая (версия до ролей) — новый фронт со старой базой не заработает, и наоборот.
- **Выкатка на прод — в самом конце, вместе с владельцем проекта**, строго по порядку ниже («Выкатка на прод»).
- Коммиты — по-русски, коротко, без Co-Authored-By и пометок ИИ.
- Секретный ключ Supabase (service role) — только в Edge Function.

## Первый день

1. `npm install`, `npm test` (37 тестов, все зелёные), `npm run dev` → http://localhost:5177.
2. Без `.env.local` — локальный режим (Postgres в браузере). На пустой главной — «Заполнить демо-данными».
3. После заполнения вы — Анна (CEO). Профиль → «Войти как…» → «Разработчик» (CEO + режим разработчика), затем ⌥D → «Смотреть как» — пройти по ролям: CEO (Анна), PM (Олег — Gold, Екатерина — RF и MVP), RM (Сергей), лиды (Мария — дизайн, Дмитрий — iOS), сотрудники (Алексей, Юлия, Ирина, Павел).
4. Пройти флоу руками: CEO «Новое приложение» → PM «Разложить» → этапы → «Передать в релиз» → RM «Отправил в Apple» / «Вышло в стор» / «Реджект». То же одной кнопкой — шорткат «Демо-процесс» в режиме разработчика.
5. Прочитать [docs/CONCEPT.md](docs/CONCEPT.md) и раздел «Принципы интерфейса» ниже.

### Выкатка на прод — строго по порядку

Если обновить только базу, текущий сайт закроет доступ всем; если только фронт — новый фронт не заработает со старой базой.

1. Supabase → SQL Editor: выполнить `supabase/schema.sql` целиком (идемпотентный, можно повторять; сам переводит старые данные — проверено обновлением с прод-версии схемы).
2. Сразу там же назначить себя CEO и включить режим разработчика:
   ```sql
   update people set access = 'superadmin', active = true where lower(email) = 'norinnort4@gmail.com';
   update people set is_dev = true where lower(email) = 'norinnort4@gmail.com';
   ```
3. Edge Functions → `admin-users` → задеплоить код из `supabase/functions/admin-users/index.ts` (новая или обновить существующую), Verify JWT включён. **Обязательно:** функция менялась — роли RM и Lead, исправлена проверка прав (раньше модератор мог сменить пароль супер-админу).
4. Слить изменения в `main` → GitHub Actions задеплоит сайт.
5. Проверить вход (CEO), затем:
   - **Люди и доступы:** роли — прежние модераторы стали PM, назначить RM и лидов; позиции и команды (команды при миграции ставятся по позиции, ASO → Other).
   - **PM видят только юниты, где они в составе** (раньше модератор видел всё) — добавить PM в состав их юнитов.
   - **Юниты:** завести Gold / RF / MVP (или переименовать существующие), в каждом — PM, RM, лиды, сотрудники; ревью юнитов — Автоматизации → Правила юнитов.
   - **Приложения:** создать (CEO → «Приложения» → «Новое приложение»); статусы, поля приложения и настройки релиза — шестерёнка там же.

Решение заказчика: выкатываем **в самую последнюю очередь**, после остальных пунктов плана, одним заходом.

## Локальный режим — важно

- База хранится в браузере: у каждой вкладки превью Claude, у обычного окна и у инкогнито — своя. Заказчик видит только свою.
- Работает одна вкладка (замок Web Locks): вторая показывает «Tasks уже открыт в другой вкладке» — иначе вкладки затирают данные.
- Профиль → «Очистить локальную базу» — пустая тулза (вход — «Разработчик»); «Заполнить демо-данными» — юниты Gold / RF / MVP, все роли и приложения на всех стадиях; Режим разработчика → «Демо-процесс» — то же поверх текущей базы как тестовые данные.
- Dev-сервер отдаёт код с `Cache-Control: no-store` — после правок хватает ⌘R.

## Как работать

```bash
npm install
npm run dev      # http://localhost:5177 — без .env.local это локальный режим (Postgres в браузере)
npm test         # тесты логики и прав на настоящем Postgres (PGlite) со схемой из supabase/schema.sql
npm run build
```

- Локальный режим: «Заполнить демо-данными» на пустом дашборде; проверка ролей — Режим разработчика (⌥D) → «Смотреть как» или профиль → «Войти как…».
- Вся бизнес-логика — `web/src/backend.js` (тот же код работает с Supabase и PGlite). Новая логика → тест в `test/`.
- Схема — только идемпотентные изменения в `supabase/schema.sql` (`add column if not exists` и т.п.).
- Права — в базе (RLS/триггеры), интерфейс только прячет недоступное.
- Коммиты — по-русски, коротко; без подписей ИИ / Co-Authored-By.

## Принципы интерфейса (от заказчика)

- Не уводить пользователя: задачи открываются поверх, мелкие правки — прямо в строке.
- Без «мельтешения»: никаких раскрывающихся панелей, которые прыгают; стабильные списки, плавные изменения.
- Админ тоже выполняет задачи: статистика задач и «Требует внимания» — важны, не убирать.
- Каждой роли — своё: CEO не видит шума декомпозиции (Default), PM — свои юниты, RM — только релизы, сотрудник — свои задачи по юнитам.
- Блоки главной должны нормально жить и в широкой, и в узкой колонке (container queries; у grid-контейнеров `grid-template-columns: minmax(0, 1fr)`).
- Клик по сущности (юнит, плитка обзора) — панель справа или список на месте, а не переход на другую страницу; переход — только явной кнопкой.
- Значки без подписей непонятны — колонки подписывать.
- Внутри поля выбора — текст и цветные точки, как у обычного списка; чипы — только для показа.
- Настройки — наглядно и интерактивно: перетаскивание за ручку, меню с галочками, правка на месте; без форм-списков и стрелок ↑↓.
- Автоматика уведомляет всегда, даже если человек сделал действие сам.
- Сложный UX — сначала 2–3 варианта заказчику (по одному вопросу, с рекомендацией), потом делать.
